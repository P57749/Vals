1. Propósito, alcance y convenciones

Este documento define las restricciones de integridad que debe satisfacer todo estado válido de la base de datos del sistema. Se derivan de los requerimientos informacionales y de sus reglas de información, del documento de requerimientos funcionales y del enunciado del proyecto. Cada restricción indica su origen y el mecanismo con que se garantiza en PostgreSQL.

Las restricciones son condiciones sobre los datos. Las reglas que dependen de quién ejecuta una operación (permisos, visibilidad) se tratan aparte en la sección 12, porque no se expresan sobre el estado de la base de datos.

1.2 Origen de cada restricción

  • RI-xx Se deduce directamente de los requerimientos informacionales o de sus reglas (RI-R1 … RI-R8).
  • MER Se deduce de las cardinalidades o de la estructura del diagrama entidad-relación.
  • RF Se deduce de los requerimientos funcionales o del enunciado.
  • DD Es una decisión de diseño adoptada por el equipo para completar un dato que el enunciado, el MER y los requerimientos no especifican. La justificación de cada una está en la sección 15.

1.3 Notación

Las restricciones complejas se formalizan en lógica de primer orden sobre las relaciones del esquema. Se usa t.A para el valor del atributo A en la tupla t, y ⇒, ∧, ∨, ¬, ∀, ∃ con su significado habitual. En el texto se usan los nombres de los requerimientos (camelCase, por ejemplo idHorario). En el SQL se usa snake_case (id_horario), que es la convención de PostgreSQL y de EF Core con UseSnakeCaseNamingConvention.

Lectura de las cardinalidades del MER. En el diagrama, la etiqueta (mín, máx) junto a una entidad indica con cuántas instancias de esa entidad se relaciona una instancia de la otra. Ejemplo: ESTUDIANTE (0,N) — Pertenece — (1,1) GRUPO se lee “cada estudiante pertenece a exactamente un grupo; un grupo tiene de cero a N estudiantes”. Esta lectura es coherente con todas las interrelaciones del diagrama y con la redacción de los requerimientos informacionales, y es la que se usa en la sección 7.

6. Restricciones de integridad referencial (RR)

Por defecto toda FK es obligatoria (NOT NULL) y se declara con ON DELETE RESTRICT y ON UPDATE RESTRICT. El sistema guarda historial académico (horarios, asistencias, revisiones) que no debe desaparecer en cascada. Para dar de baja usuarios, aulas o períodos se usa baja lógica mediante el atributo estado o activo. Las excepciones a esta regla son las de la tabla.

7. Restricciones de cardinalidad y participación (RP)

Las cardinalidades de esta sección salen del MER (lectura explicada en 1.3). Una FK NOT NULL garantiza un mínimo de 1 en el lado que lleva la FK. En cambio, un mínimo de 1 en el otro sentido (“un programa incluye una o más asignaturas”) no se puede expresar con una FK. Para esos casos se usan triggers de restricción diferidos, que se comprueban al confirmar la transacción (sección 13.4).

9. Restricciones semánticas (RS)

Son las reglas de negocio que involucran varias tuplas o varias relaciones. RS-01 a RS-08 formalizan las reglas de información RI-R1 a RI-R8, y el resto se deducen de los requerimientos funcionales y del MER. RS-05, RS-15, RS-23 y RS-24 son restricciones de ciclo: aparecen porque en el MER hay dos caminos entre las mismas entidades, y los dos tienen que llevar a la misma instancia.

13.3 Trigger de permiso (RS-03)

CREATE FUNCTION fn_rs03_puede_generar() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  IF NOT EXISTS (SELECT 1 FROM coordinador_programa cp
                  WHERE cp.id_usuario  = NEW.id_coordinador
                    AND cp.id_programa = NEW.id_programa
                    AND cp.puede_generar) THEN
    RAISE EXCEPTION 'RS-03: el coordinador % no puede generar horarios del programa %',
          NEW.id_coordinador, NEW.id_programa
          USING ERRCODE = 'check_violation';
  END IF;
  RETURN NEW;
END $$;

CREATE TRIGGER tg_rs03_puede_generar
  BEFORE INSERT ON horario
  FOR EACH ROW EXECUTE FUNCTION fn_rs03_puede_generar();

El trigger se dispara solo en INSERT: el permiso se exige en el momento de generar. Los atributos que comprueba no pueden cambiar después (RX-03).

13.4 Participación total con trigger diferido (RP-07)

CREATE FUNCTION fn_rp07_horario_con_bloques() RETURNS trigger LANGUAGE plpgsql AS $$
DECLARE v_id int := CASE TG_TABLE_NAME WHEN 'horario' THEN NEW.id_horario
                                       ELSE OLD.id_horario END;
BEGIN
  IF EXISTS (SELECT 1 FROM horario WHERE id_horario = v_id)
     AND NOT EXISTS (SELECT 1 FROM horario_bloque WHERE id_horario = v_id) THEN
    RAISE EXCEPTION 'RP-07: el horario % debe tener al menos un bloque', v_id;
  END IF;
  RETURN NULL;
END $$;

CREATE CONSTRAINT TRIGGER tg_rp07_alta AFTER INSERT ON horario
  DEFERRABLE INITIALLY DEFERRED
  FOR EACH ROW EXECUTE FUNCTION fn_rp07_horario_con_bloques();

CREATE CONSTRAINT TRIGGER tg_rp07_baja AFTER DELETE ON horario_bloque
  DEFERRABLE INITIALLY DEFERRED
  FOR EACH ROW EXECUTE FUNCTION fn_rp07_horario_con_bloques();

El mismo patrón se aplica a RP-02, RP-03, RP-12, RP-13 y RE-02. El trigger es diferido porque, dentro de la transacción, primero se inserta el horario y después sus bloques: la comprobación debe hacerse al COMMIT. En EF Core, ambas inserciones van en el mismo SaveChanges, que se ejecuta en una sola transacción.

13.5 Exclusión temporal de aulas (RS-07)

CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE sesion
  ADD CONSTRAINT rt03_horas CHECK (hora_inicio < hora_fin),
  ADD CONSTRAINT rs07_aula_sin_solapamiento EXCLUDE USING gist (
        id_aula WITH =,
        tsrange(fecha + hora_inicio, fecha + hora_fin, '[)') WITH &&
      ) WHERE (estado <> 'CANCELADA');

El intervalo semiabierto [) permite sesiones consecutivas (una termina a las 10:00 y la siguiente empieza a las 10:00) sin que se consideren solapadas. La misma técnica, con daterange, resuelve RS-20.

13.6 Transición de estados (RX-01)

CREATE FUNCTION fn_rx01_transicion_horario() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  IF NEW.estado IS DISTINCT FROM OLD.estado AND NOT (
       (OLD.estado = 'GENERADO' AND NEW.estado IN ('VALIDADO','RECHAZADO')) OR
       (OLD.estado = 'VALIDADO' AND NEW.estado IN ('APROBADO','RECHAZADO'))
     ) THEN
    RAISE EXCEPTION 'RX-01: transición de horario % -> % no permitida',
          OLD.estado, NEW.estado USING ERRCODE = 'check_violation';
  END IF;
  IF (NEW.fecha_creacion, NEW.id_coordinador, NEW.id_programa, NEW.id_periodo, NEW.id_parametro)
     IS DISTINCT FROM
     (OLD.fecha_creacion, OLD.id_coordinador, OLD.id_programa, OLD.id_periodo, OLD.id_parametro) THEN
    RAISE EXCEPTION 'RX-03: los datos de generación del horario % son inmutables', OLD.id_horario;
  END IF;
  RETURN NEW;
END $$;

CREATE TRIGGER tg_rx01_horario BEFORE UPDATE ON horario
  FOR EACH ROW EXECUTE FUNCTION fn_rx01_transicion_horario();

RD-15Estados de la asignación: ACTIVA, ANULADA.Un cambio de horario anula la asignación anterior en vez de borrarla. Así se conserva el historial que pide RI-R8.
RD-16Estados de asistencia: PRESENTE, AUSENTE, JUSTIFICADO.Separar la ausencia justificada hace más fiables las tasas de inasistencia de las consultas 4 y 6.
RD-17Decisión de la validación: VALIDADO, NO_VALIDADO.La validación es una decisión binaria. El rechazo con criterios es tarea del jefe (RD-18).
RD-19Estados de la solicitud: PENDIENTE, EN_ATENCION, RESUELTA.Los RF piden registrar “todo el proceso (estados y fechas)”.
RT-04Una autorización concede al menos un permiso.Una fila de CoordinadorPrograma sin ningún permiso no tiene significado y confundiría las consultas de autorización.
RT-09Una validación negativa lleva observaciones.Permite saber por qué se rechazó y completa la información de la consulta 3.
RC-03(nombre, planEstudio) es único en ProgramaAcademico.Evita registrar dos veces el mismo programa. Permite que un programa con el mismo nombre exista en planes de estudio distintos.
RC-04El nombre es único en Asignatura, Grupo y Edificio.Evita catálogos con entradas duplicadas que dividirían las estadísticas.
RC-05(idEdificio, nombre) es único en Aula.Un aula se identifica por su nombre dentro de su edificio. Edificios distintos pueden tener aulas con el mismo nombre.
RC-06El nombre del período es único.El nombre (por ejemplo, “2026-2027 S1”) es como los usuarios identifican el período.
RC-08Criterio de bloque duplicado: misma asignatura, mismo tipo y misma descripción normalizada.Convierte RI-R1 en un criterio objetivo que la propia base de datos puede verificar con un índice único.
RC-13Un coordinador valida un mismo horario una sola vez.Evita validaciones repetidas que inflarían la consulta 3.
RC-15Como máximo una solicitud abierta por estudiante y horario de origen.Evita solicitudes duplicadas simultáneas sobre el mismo cambio.
RP-08Cada sesión ocurre en exactamente un aula.Sin aula no se puede registrar la ocupación (RI-20) ni aplicar RS-07. Completa una cardinalidad que falta en el MER.
RP-09Cada aula pertenece a exactamente un edificio.Lo dice RI-13. Completa una cardinalidad que falta en el MER.
RE-04Un estudiante no puede tener otro rol.Separación de funciones: un estudiante no debe generar, validar ni revisar horarios.
RS-05Quien valida un horario no es quien lo generó.Separación de funciones: la validación es un control de calidad cruzado.
RS-13El jefe solo revisa horarios ya validados.Fija el orden entre RI-17 y RI-18: el jefe revisa lo que ya pasó el control del coordinador.
RS-14Los coordinadores de apoyo y de resolución están autorizados en el programa.Solo un coordinador del programa conoce y puede modificar sus horarios.
RS-17Solo se usan aulas disponibles, y los laboratorios solo en aulas de tipo laboratorio.Evita programar sesiones imposibles de impartir. Requiere el atributo Aula.tipo (sección 14).
RS-18La cantidad de estudiantes asignados no supera la capacidad del aula.Un horario que no cabe en sus aulas no se puede impartir.
RS-19Un estudiante no tiene dos sesiones activas que se solapen.Interpreta la “doble asignación” del enunciado también como choque de horas, no solo como duplicado de horario.
RS-20Los períodos no se solapan y hay como mucho uno activo.Sin esta regla, el análisis “por período” del histórico (RI-20) sería ambiguo.
RS-21Un período cerrado no admite cambios.El histórico consolidado (RH-02) no debe cambiar después de cargarse.
RX-04Una sesión impartida o cancelada no cambia de estado; una sesión con asistencias no se cancela.Protege la coherencia entre las sesiones y las asistencias ya registradas.
RX-05El período avanza PLANIFICADO → ACTIVO → CERRADO, sin vuelta atrás.Reabrir un período invalidaría el histórico ya cargado.
RX-06Una asignación anulada no se reactiva.El historial de cambios queda como una secuencia de asignaciones, sin estados reescritos.
RX-08La clasificación de un bloque no cambia si está en un horario aprobado.Las consultas 2, 4 y 6 agrupan por complejidad y asignatura. Si cambiaran, se alterarían los reportes del pasado.
